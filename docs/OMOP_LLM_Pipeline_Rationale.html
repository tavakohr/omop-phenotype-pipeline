OMOP LLM Pipeline — Rationale & Worked Examples

H. Tavakoli, MD  ·  omop-phenotype-pipeline  ·  May 2026
This document answers two questions raised during project planning:
(1) Why does an LLM add value when SQL can resolve concept IDs directly?
(2) What does the full combined system enable that no single component can do alone?
1

The Fundamental Question: Why Not Just Use SQL?

"When I can run SELECT concept_id FROM cdm.concept WHERE concept_name = 'Complication due to diabetes mellitus' and extract the concept_id from the gold standard, what additional benefit does the LLM provide? I still do not get how the LLM cannot run the proper query to find the concept_id."
The confusion arises from a framing issue. SQL and the LLM are not solving the same problem — they solve two completely different problems in sequence.

Problem A — Enumeration (LLM's job)

"What are all the conditions, drug ingredients, measurements, and procedures that together define a T2DM patient cohort?"

This requires clinical reasoning and medical knowledge. There is no SQL query that can answer it — you cannot query a database for "concepts relevant to T2DM" because relevance is a clinical judgment, not a string match.

The OMOP vocabulary has ~5 million concepts. The LLM's training on medical literature lets it enumerate the right ones by name.

Problem B — Lookup (SQL's job)

"Given the name 'Metformin', what is its standard concept_id, and is it an active, non-invalid concept?"

This requires vocabulary table access. SQL does this perfectly. An LLM cannot — concept_ids are arbitrary integers that LLMs cannot reliably memorise or reproduce without hallucinating.

Your query solves Problem B exactly. It does nothing for Problem A.

Core Principle

Your SQL query WHERE concept_name = 'Complication due to diabetes mellitus' only works if you already know that this concept belongs in the phenotype. The hard problem is knowing which 18 (or 70, or 194) concept names to look up in the first place. That enumeration is the intellectual work the LLM automates.

Think of it this way: a medical coder at a hospital never memorises concept_ids — they navigate ATHENA by searching concept names. The LLM mimics the clinical reasoning step that decides which names to search. SQL then mimics the lookup step the coder performs in ATHENA.

Why Can't the LLM Write and Run the SQL Itself?

In principle you could give an LLM database access. But even then, there is no SQL query that answers "find me all concepts clinically relevant to T2DM." Relevance is not encoded in the vocabulary schema — it is clinical judgment. A LIKE '%diabetes%' query returns hundreds of irrelevant concepts (diabetes insipidus, diabetic retinopathy as a standalone, etc.) and misses drug ingredient concepts that have no "diabetes" in their name.

Additionally, LLMs hallucinate concept_ids when asked to produce them directly. They output plausible-looking integers that do not exist in the vocabulary. This is why the pipeline design rule states: the LLM must never output concept_ids. The response_parser.R validator enforces this and stops with an error if any bare integers appear in the LLM output.

What the Combined System Does

LLM → generates a list of medically correct concept names
SQL → maps each name to a verified, standard, active concept_id
CONCEPT_ANCESTOR → expands each anchor concept to all clinical descendants
Evaluator → scores the result against the expert gold standard

Each layer does only what it is uniquely suited to do. Removing any one layer collapses the pipeline.

The Research Question

Given only a plain-language physician brief, how closely can an LLM's concept enumeration match the gold-standard phenotype curated by OHDSI experts?

The F1 score quantifies that gap. If LLMs reach F1 ≥ 0.75, they can automate the first draft of a phenotype definition — cutting curation time from days to minutes.

Scenario 2 — Benchmarking Claude vs Gemini Across Six Phenotypes

A health AI startup is building a phenotype auto-curation product. They must decide: Claude Opus 4.6 or Gemini 2.5 Flash? They have clients in five therapeutic areas. 6 phenotypes × 2 models × 3 trials = 36 automated runs.
Goal: reproducible head-to-head benchmark identifying which model wins per disease area and where both fail badly enough to require a better brief.

Pipeline runs overnight — run_pipeline.R outer loop

# 6 phenotypes × 2 models × 3 trials = 36 API calls, fully automated
for (ph in phenotypes) # t2dm, copd, trd, cardiac_valve_af, liver_injury, drug_pancreatitis
  for (model in models) # claude_opus_4_6, gemini_flash
    for (trial in 1:3)
      run_phenotype(ph, model, trial)
# Each run: brief → API → parse JSON → SQL lookup → ancestor expansion → score → append to CSV

Three Actionable Decisions — Only Visible With the Full System

Decision 1 — Use Claude for most phenotypes; route cardiac to Gemini

Claude wins 4 of 6 phenotypes. But Gemini outperforms Claude specifically on Cardiac Valve AF (F1 0.61 vs 0.52). In a production pipeline you would route cardiac phenotype requests to Gemini and all others to Claude. This model-routing insight is invisible without a multi-phenotype, multi-model benchmark.

Decision 2 — TRD and Drug Pancreatitis need better briefs, not better models

Both models score F1 ≈ 0.22–0.24 on TRD. The error analysis shows the same false negatives for both — specific antidepressant formulation codes and TRD-specific ICD-10 codes missing from the brief. This is a brief quality problem, not a model capability problem. The benchmark tells you exactly where to invest clinician time rather than wasting budget on a more expensive model.

Decision 3 — Ancestor expansion provides a consistent and measurable lift

Ancestor-aware F1 is systematically 15–20 points higher than exact F1 across all phenotypes and both models. This quantifies the engineering value of CONCEPT_ANCESTOR traversal. Removing the expansion layer would meaningfully degrade performance. This is only measurable when you run the full 4-layer system end-to-end and compare exact vs ancestor-aware scoring.

Summary — What Each Component Contributes

Component What it can do alone What it cannot do alone
Physician Brief Capture clinical intent in plain English Cannot map clinical language to OMOP vocabulary; cannot enumerate exhaustively without curation support
LLM (Claude / Gemini) Enumerate clinically relevant concept names from a plain-language brief; classify domain and exclusion intent Cannot produce verified concept_ids; cannot query a database; cannot evaluate its own output against a gold standard
SQL / PostgreSQL Map any concept name to a verified standard concept_id via the 5-tier cascade; expand via CONCEPT_ANCESTOR Cannot decide which concept names are clinically relevant; cannot evaluate phenotype completeness
Gold Standard (OHDSI) Provide the expert-curated reference set for evaluation Cannot be used as input — it is the answer, not the method
Full Pipeline Brief → LLM → SQL lookup → Ancestor expansion → F1 scoring → Error analysis → Brief iteration. Produces a validated, reproducible OMOP concept set from plain English, with a quantified quality score and a precise error report telling the clinician exactly what to add next.
